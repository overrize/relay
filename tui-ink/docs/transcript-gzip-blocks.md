# 单 gzip 内部分块索引与断点续建

2026-10-21。本轮在已有“归档之间的断点”之外，补齐同一个大型 gzip 内的解压与索引断点。原始 `.mem.gz`、retention baseline、账本格式不变。

## 实现

`ArchiveChunkStore` 在 `.spawn/transcript-cache/archive-cache.sqlite` 保存可丢弃缓存：

- 固定版本 pako 的 gzip/DEFLATE 状态：压缩流位置、未消费输入、位缓冲、滑动窗口、字典表、CRC/长度状态；不是从头 gunzip 再跳过事件。
- JSON 解析状态、部分记录、UTF-8 未完成字节及 hash-wasm 的源摘要状态。每约 512 KiB 解压输出或压缩输入保存一次事务断点。
- 已完成事件分块、块序号范围和摘要；压缩输入的块摘要存独立规范化表，仅增量追加。断点不反复序列化全部压缩块清单。
- 状态与块清单的摘要链、源身份与 codec/Node 主版本标识。格式不兼容或损坏时丢弃缓存，从原归档校验。

全部 gzip member 的 CRC、原归档 body digest、事件数量和序号范围通过后才提供事件；未完成的转换块不会成为用户可见的部分历史。历史归档经过保留策略过滤后可以缺号，末尾 hash 也可能属于被过滤事件，按既有格式处理。

索引读取已验证缓存时按 `last_seq > cursor` 查范围，只解析相关事件块。每个事件块消费完成后，可事务提交同一归档内的 transcript checkpoint。构建 manifest 仅改写最后一个未完成来源，已完成来源不重复写入；内存中的 prefix 也增量维护。

恢复时会读取已缓存的**压缩前缀**做块哈希校验，检测大小/时间戳不变的原地改写。这是有意保留的来源完整性成本，不能宣称零 I/O 或绝不再扫描任何字节；避免的是已完成前缀的重复 DEFLATE 和 JSON 解析。完整 transcript 索引命中的普通后续翻页不进入这条解压路径。

## 配额、兼容和边界

- 缓存与 transcript SQLite 索引合并计入 `SPAWN_TRANSCRIPT_INDEX_MAX_BYTES`。旧来源缓存按最近使用顺序回收；配额缩小后可删除派生缓存；账本和归档不变。
- 配额不能容纳当前归档派生数据时，回退既有校验流读取，返回真实结果并通过 `index.archive.quotaFallbacks` 标明。不能保证这类归档仍具有内部续建性能。
- 既有非规范化/手工排版 v1 JSON 继续走旧 verified decoder；该兼容分支不承诺新块索引或低内存。不能借“兼容”虚报所有旧布局均可 seek。
- 单条事件自身特别大时，部分 JSON 记录仍需要相应内存和断点空间；本轮没有宣称单记录无界大也恒定内存。
- 首次读取旧的单流 gzip 仍需完整校验一次后才发布历史页；UI 显示压缩流进度并保持 PM 通道。后续恢复可利用内部状态，不能把 gzip 变成天然随机访问格式。
- pako/序列化引擎升级可能使派生状态失效并重建；源数据不受影响。SQLite 事务日志和瞬时内存是运行开销，持久缓存配额不是整个进程/磁盘峰值硬上限。

## 真实验证发现的额外故障

最终真实 API 复跑曾出现模型把 `agent.done.evidence` 写为字符串。旧投影代码在写入后调用数组方法抛错，导致内存 seq 与 offset 不一致，表现为账本完整性错误；单独校验磁盘哈希链并无断裂。本轮修复：入口拒收该错误形状并记录原因；旧日志中的相同记录可回放为失败报告；投影先在隔离副本完成后才持久发布，计算失败不会先写入坏事件或污染原状态。加入拒收、失败原子性、旧日志重启回归。这不是忽略失败后只报告某次成功。

## 验收矩阵

过去连续多轮的问题在于局部改动之后只列出新限制，没有先把端到端故障模型和完成条件列全。本轮用下表约束同一交付：

| 维度 | 验证 | 结果 |
| --- | --- | --- |
| 旧格式 | 规范 v1、非规范 header、Unicode/转义、跨块、串接 gzip member、过滤后缺号及末尾不同 anchor | 单元回归 |
| 来源完整性 | 截断、错误 CRC/body digest、原地改写，即使元数据不足以区分也不使用旧解压结果 | 不发布未验证条目 |
| 派生缓存 | 状态/根摘要损坏、事件块损坏、配额 0/不足/缩小 | 重建或明确回退，不修改源 |
| 内部恢复 | 真进程强杀转换，另一个进程接续；再在同一归档的索引中强杀并重启 | 原 inflater/parser 状态续建，消息不重不丢 |
| 大小与写入 | 压缩块摘要独立表增量追加；来源 manifest 仅更新尾项；按范围读事件块 | 避免每个断点重写全部来源/输入清单 |

| 目标与重启 | 真实 `/revise` 取消旧任务，不写 obsolete.txt，写 new.txt，强杀后 `/resume` 读取新目标产物 | 真实 API 端到端验证 |

| 发布 | typecheck/build、完整测试、headless、精确提交 SHA 的 Linux/Windows CI | 以本轮最终测试/CI 记录为准 |

完整测试 918 项：911 通过，7 项原有 TODO；headless 82/82。真实 API 验证产物为 `.test-tmp/native23-live-mKoVnj/verification.json`，使用 7 次请求：归档与索引断点、执行中沟通、旧目标取消、草稿和强杀恢复均为 true。中途暴露的错误完成事件另有回归，不隐藏该失败。

3002 事件的约 17.5 MB 原文单归档，本机首次建索引 1593 ms，7 个后续页为 23–27 ms 且 visited=0。这是本机样本，不是跨硬件或 TB 归档的时延承诺。
