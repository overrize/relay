# 首次重建与分段元数据性能

本轮复用后台历史读取线程（最多 4 个工作区，闲置 30 秒释放），避免每页重启线程和加载基线。线程闲置不阻止进程退出；SessionController 退出时先取消历史读取。SQLite 每次查询结束关闭，缓存配额按请求传入。

每页仍校验全部来源元数据：8 路异步 stat 在写锁外运行，捕获活动文件前缀及哈希边界，校验期间的追加不会混入旧快照。主备保留清单对相同归档只检查一次大小，不使用跨查询 TTL。复用这一份来源清单，二分定位归档；首次重放最多预读 4 段，按顺序校验哈希链，每批只短暂获取一次写锁。异常时等待全部读取结束并关闭所有句柄，原始归档损坏仍拒绝返回。

## 性能证据

本机 Windows，同一份 3000 条消息 / 250 个归档的离线夹具：旧版首次 567 ms、后续 79–85 ms；本轮首次 416 ms、后续 17–20 ms。1000 条消息 / 1000 个归档：首次 550 ms、后续 42–47 ms。热页 visited=0、readBatches=0，仍逐个检查来源元数据。数据来自 `.test-tmp/native27-before.log`、`native27-final250.log` 和 `native27-final1000.log`；这是读取路径测量，不是所有机器的终端响应承诺。

复现：构建后 `node scripts/benchmark-transcript.mjs 1000 1024` 创建大量分段夹具；`node scripts/benchmark-transcript27.mjs <夹具路径> --cold` 删除该离线夹具的可重建分页缓存并测量 8 页。

## 边界

首次完整重建仍须读取、解压并验证保留历史；超大单归档的解压成本仍存在。每页新鲜元数据校验仍随分段数量增长，尚未变成常数开销；闲置释放或重启后的线程初始化成本仍在。线程池和预读有界，不改原始事件、记忆、预算及历史费用快照。
